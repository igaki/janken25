# 2025-11-07 複数ユーザログインと対戦実装調査

## 概要
異なるユーザがログインし、じゃんけん対戦ができる仕組み（リアルタイム対戦または近リアルタイム対戦）を実装するための技術選定、設計案、必要ファイル・DB変更点、検証手順を調査しました。本調査はコードの実装を行わず、実現方法の比較・推奨をまとめたものです。

## 要件（想定）
- ユーザは個別アカウントでログインできること（認証）
- ログインした複数ユーザ間で対戦ができること（対戦開始、勝敗判定、結果表示）
- 対戦履歴を永続化できること
- 基本はブラウザで動作する（既存の Thymeleaf テンプレート利用）

## 技術選択肢（利点・欠点）
1. 認証
   - Spring Security を利用
     - 利点: 標準的で拡張性が高い。フォームログイン、セッション管理が容易。
     - 欠点: 設定が多少必要。既存プロジェクトに適用する際に設定ファイル・UserDetailsService 実装が必要。

2. リアルタイム対戦の実現方法
   - WebSocket（STOMP + SockJS）
     - 利点: 双方向通信で低レイテンシ。接続管理・ブロードキャストが容易（対戦のoffer/accept、手の送信、結果通知）。
     - 欠点: サーバ側に継続接続の管理が必要。テストがやや複雑。
   - Server-Sent Events（SSE）
     - 利点: サーバ→クライアント通知が簡単。実装が比較的容易。
     - 欠点: クライアント→サーバは通常 HTTP（ポーリング）になるため双方向には不向き。
   - ポーリング（短周期のAjax）
     - 利点: 実装が単純。既存のアーキテクチャへの導入が容易。
     - 欠点: レイテンシと無駄なリクエストが増える。スケールに弱い。

3. マッチメイキング（対戦組み合わせ）
   - ロビー方式（ユーザが対戦相手を選ぶ）
   - 自動マッチング（キューに入れて先着でマッチ）
   - フレンド招待方式（特定ユーザ同士）

4. 永続化
   - 既存の MyBatis を利用して `janken_history` の拡張（対戦テーブル、マッチID、プレイヤー2の情報など）
   - トランザクション管理に注意（同時更新を避ける）

## 想定DBスキーマ（例）
- users (id, username, password_hash, display_name, ...)
- matches (match_id, player1_id, player2_id, status, created_at, finished_at)
- match_rounds / janken_history (id, match_id, player_id, hand, result, timestamp)

※ 既存プロジェクトに `janken_history` があるため、必要に応じて `matches` を追加して関連付けることを推奨。

## UIフロー（例）
1. ユーザAがログイン
2. ロビー画面で対戦相手を選ぶ／自動マッチングに参加
3. マッチ確定後、両者は対戦ページに遷移（または同一画面で WebSocket セッションを共有）
4. 各ユーザが手を選択して送信（WebSocket メッセージ）
5. サーバが両者の手を受け取り、勝敗判定を行い結果を送信
6. 結果を DB に永続化し、履歴ページで参照可能にする
